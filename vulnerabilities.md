# Security Audit Report

**Проект:** Hotel Room API (Lab 12)  
**Дата:** 2026-05-10  
**Аудитор:** AI Security Auditor

---

## Резюме

В ходе аудита выявлено **6 уязвимостей и недостатков безопасности** различного уровня риска. Критические проблемы связаны с отсутствием валидации бизнес-правил (вместимость номера, прошедшие даты).

---

## Список уязвимостей

### 1. Отсутствие валидации email
- **Уровень риска:** 🟡 **Средний**
- **Файлы:** `app/schemas.py` (`guest_email`)
- **Описание:** Поле `guest_email` валидируется только на `min_length=1`. Можно передать любую строку, не соответствующую формату email (например, `"not-an-email"`).
- **Рекомендация:** Использовать `EmailStr` из Pydantic для строгой валидации формата email.

---

### 2. Отсутствие проверки вместимости номера
- **Уровень риска:** 🟡 **Средний**
- **Файлы:** `app/main.py` (`create_booking`, `update_booking`)
- **Описание:** При создании или обновлении бронирования не проверяется, что `guests_count` не превышает `room.capacity`. Можно забронировать номер на 2 человек для 10 гостей.
- **Рекомендация:** Добавить проверку `guests_count <= room.capacity` перед сохранением бронирования.

---

### 3. Отсутствие проверки дат на "не в прошлом"
- **Уровень риска:** 🟡 **Средний**
- **Файлы:** `app/main.py` (`create_booking`, `update_booking`)
- **Описание:** `check_in` и `check_out` принимают любые даты, включая прошедшие. Это позволяет создавать бронирования задним числом, что нарушает бизнес-логику и может использоваться для фальсификации данных.
- **Рекомендация:** Добавить проверку, что `check_in >= date.today()`.

---

### 4. Отсутствие ограничений на `floor` и `room_number`
- **Уровень риска:** 🟢 **Низкий**
- **Файлы:** `app/schemas.py` (`RoomCreate`, `RoomUpdate`)
- **Описание:** Поле `floor` может быть отрицательным или нулевым. `room_number` не имеет ограничения `max_length`, что потенциально позволяет сохранять слишком длинные строки.
- **Рекомендация:** Добавить `gt=0` для `floor` и `max_length` для `room_number`.

---

### 5. Побочный эффект `print()` в бизнес-логике
- **Уровень риска:** 🟢 **Низкий**
- **Файлы:** `room_cost_calculator/bad_calculator.py`
- **Описание:** Функция `f()` содержит `print(r)`, что приводит к утечке промежуточных данных в stdout при вызове в production. Хотя это "плохая" версия для рефакторинга, она всё ещё импортируется и используется в тестах.
- **Рекомендация:** Удалить `print(r)`.

---

### 6. Отсутствие Rate Limiting и Security Headers
- **Уровень риска:** 🟡 **Средний**
- **Файлы:** `app/main.py`
- **Описание:** API не защищено от brute-force и DDoS-атак на уровне приложения. Отсутствуют базовые security-заголовки (CORS настроен по умолчанию — открыт для всех).
- **Рекомендация:** Добавить middleware с rate limiting и настроить CORS политику.
